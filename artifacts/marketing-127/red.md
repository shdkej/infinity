# Red 검증 체크리스트 — marketing-127

## 0. 검증 목적

이 문서는 `@archivenoh`의 공개 게시물 기반 Instagram 운영 전략이 현재 intent의 성공기준과 권한 경계를 지키는지, 그리고 앱/플랫폼 정보가 불완전한 상태에서 과도한 추천을 만들지 않는지를 최종 검증하기 위한 체크리스트다.

판정은 다음 세 단계로 한다.

- **PASS**: 근거와 산출물이 모두 확인되고, 미확인 사항이 명시적으로 제한되어 있다.
- **CONDITIONAL**: 전략은 보류 가능한 제안으로 유효하지만, 확인되지 않은 정보 때문에 실행·추천을 승인할 수 없다.
- **FAIL**: 근거 없는 사실화, 경계 위반, 필수 산출물 누락, 또는 불확실성을 숨긴 추천이 있다.

## 1. Intent 성공기준 검증

- [ ] 공개 게시물 **3개 이상**의 실제 URL을 확인했다.
- [ ] 각 게시물에 대해 게시일과 확인 시각을 기록했다.
- [ ] 각 게시물의 캡션 존재 여부를 구분하고, 확인된 캡션은 원문 근거와 함께 보존했다.
- [ ] 계정 식별자(`_archivenoh`)가 근거 문서와 통합안에서 일관된다.
- [ ] 게시일과 캡션 안에 적힌 사건/날짜를 혼동하지 않았다. 예: 캡션의 `2026.08.20`을 게시일로 재사용하지 않는다.
- [ ] 분석 문장마다 `직접 확인한 사실 / 그 사실에서 제한적으로 도출한 해석 / 아직 모르는 것`을 구분했다.
- [ ] 확인된 게시물에서 반복 패턴, 강점, 자기검열 완화 방향을 제안하되, 표본 수가 적다는 한계를 함께 적었다.
- [ ] 실행 제안이 1~2주 범위로 구체화되어 있다.
- [ ] 제안에는 소재 수집, 초안 규칙, 게시 전 확인, 기록할 운영 지표, 다음 재검토 조건이 포함되어 있다.
- [ ] Planner → Developer → Marketer → Operator → Red의 역할별 판단 또는 산출물 흔적이 남아 있다.
- [ ] 최종 통합안이 공개 게시물 근거 문서와 모순되지 않는다.

**하드 게이트:** 게시물 3개, 게시일, 캡션/무캡션 상태 중 하나라도 실제 근거가 없으면 성공기준 PASS로 판정하지 않는다. 이미지·톤·타깃·성과를 HTML 메타데이터만으로 판단한 경우 FAIL이다.

## 2. 경계·권한 검증

- [ ] 작업은 공개 정보의 조사·분석·내부 전략 제안에 한정된다.
- [ ] Instagram 공개 게시, 예약 게시, 프로필 변경, 로그인, DM, 댓글, 외부 발송을 수행하지 않았다.
- [ ] 제안 문구와 실행 문구를 구분하고, 사용자의 별도 승인 없이는 공개 실행으로 읽히지 않는다.
- [ ] 외부 계정의 소유권, 접근 권한, 게시 권한을 추정하지 않았다.
- [ ] 좋아요/댓글 수가 0이거나 누락된 것을 콘텐츠 가치·실패·성공의 증거로 사용하지 않았다.
- [ ] 공개 URL의 접근 실패, private 전환, rate limit을 계정 상태나 콘텐츠 평가로 단정하지 않았다.
- [ ] 재확인이 필요할 때 원본 URL, 확인 시각, 응답/메타데이터를 보존하며 근거를 조용히 덮어쓰지 않는다.
- [ ] 개인정보, 비공개 게시물, 로그인 후 정보, 제3자 계정의 비공개 데이터를 수집 대상으로 확장하지 않았다.

**즉시 FAIL 조건:** 실제 게시·프로필 변경·DM·외부 발송이 실행됐거나, 공개 근거만으로 비공개 사실을 단정했다면 전략 품질과 무관하게 FAIL이다.

## 3. 역할별 산출물 검증

| 역할 | 필수 산출물/판단 | Red 확인 질문 |
|---|---|---|
| Planner | 목표, 표본 한계, 원본 경험 기반 운영 가설 | 이 가설이 게시물 1건 이상의 관찰을 넘어서 계정의 확정 정체성으로 과장되지 않았는가? |
| Developer | 근거표, 재현 절차, 사실/제한/해석 분리 | 다른 사람이 같은 URL과 확인 시각으로 핵심 사실을 재확인할 수 있는가? |
| Marketer | 톤/포맷 가설, 1~2주 콘텐츠 실험안 | 한 캡션을 고정 톤·타깃·성장 전략으로 오인하지 않았는가? 실험과 확정 결론을 구분했는가? |
| Operator | 손기록 항목, 재확인 조건, 승인 대기 상태 | 실행 지표가 공개 성과로 과장되지 않았는가? 실패/접근 제한 시 중단 규칙이 있는가? |
| Red | 통합안에 대한 근거·경계·불확실성 판정 | 통합안의 모든 강한 표현에 근거 또는 명시적 가정이 있는가? |

추가로 다음을 확인한다.

- [ ] 역할별 산출물이 서로 다른 빈도, 톤, 승인 상태를 말하지 않는다. 불일치가 있으면 통합안에 결정 근거가 기록되어 있다.
- [ ] Developer가 코드를 만들지 않은 경우에도 “해당 없음”과 대체 검증물(근거표/재현 절차)을 남겼다.
- [ ] Operator의 24시간/7일 재확인은 성과 측정이 아니라 공개 상태와 근거 보존 목적임을 명시했다.
- [ ] Red가 제안의 실행 가능성과 공개 실행 권한을 별개로 판정했다.

## 4. 불확실한 앱 정보에 대한 과도한 추천 방지 기준

Instagram, 분석 도구, 예약 도구, 연결 앱 등 앱 관련 정보는 다음 네 상태로만 기록한다.

| 상태 | 의미 | 허용되는 표현/행동 |
|---|---|---|
| 확인됨 | 공식 문서, 실제 공개 화면/응답, 또는 재현 가능한 기록으로 기능·접근 조건이 확인됨 | 조건을 붙인 제한적 추천 가능 |
| 부분 확인 | 일부 기능/요금/지역/계정 조건만 확인됨 | 확인된 부분만 설명하고 나머지는 보류 |
| 미확인 | 기능, 연동, 최신 상태, 권한, 비용 중 핵심 항목을 확인하지 못함 | 추천하지 말고 확인 질문 또는 대안 절차 제시 |
| 충돌 | 출처·시점·화면 간 정보가 서로 다름 | 충돌을 명시하고 최신/공식 근거 확인 전 추천 금지 |

### 추천 전 필수 검증

- [ ] 추천하려는 앱의 정확한 제품명, 플랫폼, 계정 유형, 사용 지역을 식별했다.
- [ ] 추천의 핵심 주장(예: 예약 게시, 분석 제공, Instagram 연동, 자동 발송)이 실제로 필요한 기능인지 분리했다.
- [ ] 각 핵심 주장에 출처와 확인 시각이 있다. 검색 결과 제목, 광고 문구, 과거 기억만으로 “지원한다”고 쓰지 않는다.
- [ ] 무료/유료, 요금, 제한량, API·로그인 필요 여부, 게시 권한, 개인정보 접근 범위를 확인했거나 미확인으로 표시했다.
- [ ] 최신성에 민감한 정보는 현재 확인 시점을 적었다. 오래된 리뷰·캐시·스크린샷을 현재 기능의 증거로 재사용하지 않는다.
- [ ] 앱의 존재와 이 작업에 적합하다는 판단을 구분했다. 존재 확인만으로 “최적”, “가장 좋음”, “추천”이라고 결론내리지 않는다.
- [ ] 대안 앱을 여러 개 나열하기 전에 사용자의 실제 제약(예산, 자동화 필요, 로그인 허용, 지역, 모바일/웹)을 확인했다.
- [ ] 핵심 조건이 하나라도 미확인이면 강한 추천을 보류하고, `확인되면 고려할 수 있는 후보` 수준으로 낮췄다.
- [ ] 앱을 사용하지 않아도 되는 수동 절차가 있으면 함께 제시했다.
- [ ] 앱 추천이 공개 게시·외부 발송을 자동 실행하는 방향으로 경계를 넓히지 않는다.

### 표현 강도 게이트

다음 표현은 핵심 기능·조건이 모두 확인된 경우에만 허용한다: `추천`, `적합`, `가장 좋다`, `자동으로 된다`, `안전하다`, `무료다`, `연동된다`.

그 외에는 다음처럼 낮춰 쓴다.

> “현재 확인한 정보만으로는 기능/권한/비용을 확정할 수 없으므로 추천을 보류한다. 공식 기능 페이지와 실제 계정 조건을 확인한 뒤 후보로 비교한다.”

앱 정보가 불확실한데도 특정 앱을 바로 선택하게 하거나, 확인되지 않은 기능을 전제로 1~2주 운영안을 설계했다면 **FAIL**이다. 불확실성을 표시하고 수동·저위험 대안을 제시했다면 **CONDITIONAL**로 통과시킬 수 있다.
