# marketing-127 Marketer — Threads 브랜드 계정 후보 평가 프레임

## 역할 판단

이 작업의 질문은 “예쁜 계정명이 무엇인가”가 아니라 **앱 하나를 전담하는 Threads 브랜드 계정으로 오래 운영할 수 있는 이름인가**다. 후보명은 게시물 한두 개의 화제성보다 다음 네 가지를 먼저 통과해야 한다.

1. 계정이 무엇을 위한 공간인지 처음 보는 사람이 추측할 수 있는가.
2. 앱의 핵심 문제와 사용 장면을 담되, 기능 변경 때 발목을 잡지 않는가.
3. Threads의 짧은 관찰·대화형 게시물로 반복 사용해도 어색하지 않은가.
4. 개인 계정, 기존 브랜드, 기능명, 캠페인명과 혼동될 위험이 낮은가.

앱 카테고리·핵심 문제·첫 사용자가 아직 확정되지 않았다면 이름의 의미를 과도하게 단정하지 않는다. 이 문서는 후보를 좁히는 내부 판단안이며, 핸들 선점·계정 생성·프로필 변경·공개 게시를 포함하지 않는다.

## 평가 프레임

### 1차 하드 게이트

다음 중 하나라도 해당하면 점수와 관계없이 `hold` 또는 `reject`한다.

| 게이트 | 통과 기준 | 탈락 예시 |
| --- | --- | --- |
| 역할 명료성 | 개인 일상 계정이 아니라 앱 전담 계정으로 설명 가능 | 사람 이름·여행 일기처럼만 읽히는 이름 |
| 발음·기억 | 한국어로 읽고 말하기 쉽고, 한 번 들은 뒤 다시 찾을 단서가 있음 | 철자 설명이 길거나 숫자·밑줄 의존 |
| 확장성 | 첫 기능 외의 인접 기능·콘텐츠·커뮤니티로 확장 가능 | 특정 기능, 특정 OS, 일시적 밈에 고정 |
| 안전성 | 타 브랜드·상표·유명 서비스의 공식 계정으로 오인될 가능성이 낮음 | `official`, `support`, 경쟁사명 결합 |
| 운영 가능성 | Threads 표시명·소개문·핸들 후보로 실제 입력 가능한 길이 | 지나치게 긴 문구, 플랫폼 정책에 걸릴 수 있는 표현 |
| 증거 경계 | 확인하지 않은 핸들 가용성·상표 상태를 사실처럼 말하지 않음 | “사용 가능”, “상표 문제 없음” 단정 |

### 2차 가중 점수

하드 게이트를 통과한 후보만 5점 척도로 평가한다. `1`은 매우 약함, `3`은 조건부, `5`는 명확한 강점이다.

| 항목 | 비중 | 판단 질문 |
| --- | ---: | --- |
| 앱 연결성 | 25 | 앱이 해결하는 문제나 사용 장면과 자연스럽게 연결되는가? |
| Threads 적합성 | 20 | 짧은 관찰, 질문, 사용자 반응을 계정 이름 아래 계속 만들 수 있는가? |
| 기억성·발음성 | 20 | 듣고 쓰고 검색하기 쉬운가? 한국어/영어 발음이 갈라지지 않는가? |
| 확장성 | 15 | 앱 버전·기능·콘텐츠 축이 바뀌어도 유지되는가? |
| 브랜드 톤 | 10 | 앱의 약속과 원하는 온도(실용·차분·실험 등)가 맞는가? |
| 리스크 여유 | 10 | 오인, 상표, 철자 충돌, 부정적 연상에 여유가 있는가? |

총점은 `항목별 점수 ÷ 5 × 비중`으로 계산한다. 80점 이상은 `shortlist`, 65~79점은 앱 정보 보강 후 `conditional`, 64점 이하는 `drop`으로 둔다. 단, 총점이 높아도 하드 게이트 미통과면 추천하지 않는다.

## 후보 비교 시 확인할 운영 질문

각 후보에 같은 질문을 적용해 감상평이 아니라 비교 가능한 기록을 남긴다.

- “이 계정은 무엇을 관찰하고 무엇을 돕는가?”를 한 문장으로 설명할 수 있는가.
- `오늘 이 앱을 쓰며 ___을 알게 됐다` 같은 Threads 문장이 자연스럽게 붙는가.
- 사용자 문제, 제품 업데이트, 사용 팁, 실패 기록, 질문형 게시물의 다섯 포맷에 모두 붙는가.
- 계정명만 보고 앱이 모든 문제를 해결하거나 특정 결과를 보장한다고 오해하지 않는가.
- 표시명과 핸들이 달라도 검색·구두 전달에서 같은 브랜드로 회수되는가.
- 앱이 다른 카테고리로 확장되거나 이름을 바꿀 때 설명문만 바꿔도 살아남는가.

### 후보군의 역할별 분류

후보를 한 줄 순위만으로 보지 말고 다음 유형으로 태깅한다.

- **문제형:** 사용자의 반복되는 불편을 이름에 담는다. 앱 연결성은 강하지만 해결 범위를 좁힐 수 있다.
- **행동형:** 기록·정리·선택처럼 사용자의 행동을 담는다. 콘텐츠 확장성이 좋고 기능 변경에 비교적 강하다.
- **장소/세계관형:** 앱의 분위기와 기억 장치를 만든다. 차별화는 쉽지만 앱 역할 설명이 약해질 수 있다.
- **조어형:** 독자적인 브랜드 자산을 만든다. 장기적으로 강할 수 있으나 초기 설명 비용과 철자 리스크가 크다.

초기 전담 계정은 보통 `행동형`을 우선 검토하고, 앱의 핵심 문제와 첫 사용자가 명확할 때만 `문제형`을 상위로 올린다. `세계관형`·`조어형`은 소개문으로 역할을 보완할 수 있을 때 shortlist에 둔다.

## 추천 결정 규칙

Planner가 정리한 브랜드 역할과 Developer의 후보·중복 점검이 도착하면 다음처럼 결정한다.

1. 하드 게이트 통과 후보 중 총점 1위, 백업 2개를 남긴다.
2. 1위가 2위보다 8점 이상 높지 않으면, 점수보다 `앱 연결성`과 `Threads 적합성`의 세부 근거를 재검토한다.
3. 앱 정보 부족으로 1위와 2위의 의미가 달라지면 억지로 결정하지 않고 `conditional/hold`로 둔다.
4. 실제 핸들 가용성·상표·유사 계정 확인 전에는 “최종 이름”이 아니라 “추천 후보”라고 표기한다.
5. 계정 생성 또는 공개 전에는 프로필 설명, 첫 게시물 3개, 문의/지원 경로가 이름의 약속과 일치하는지 별도 검토한다.

추천 1개를 고를 때의 최소 문장 형식은 다음과 같다.

> **추천:** `[후보명]` — 앱의 `[핵심 문제/행동]`을 암시하면서 Threads에서 `[관찰/질문/사용 사례]`를 반복하기 쉽고, 기능 확장 시 이름을 바꿀 필요가 적다. 단, 핸들·상표·유사 계정은 아직 확인 전이다.

## 운영 리스크

| 리스크 | 왜 생기는가 | 운영 통제 |
| --- | --- | --- |
| 공식 계정 오인 | 계정명이 앱 회사의 고객지원·공지 채널처럼 보임 | 소개문에 비공식/공식 여부와 문의 경로를 명확히 하고 `official`, `support`를 임의로 쓰지 않음 |
| 제품 약속 과장 | 이름이 “자동 해결”, “최고”, “완벽”을 암시함 | 검증 가능한 기능·사용 장면만 약속하고 성과 보장 표현을 금지 |
| 브랜드-개인 혼합 | 운영자가 개인 경험과 제품 발화를 구분하지 못함 | 계정의 발화 주체, 제품 의견, 개인 의견을 초기에 정의 |
| 기능 종속 | 첫 기능명·버전명이 계정명에 박힘 | 행동·문제 중심 이름을 우선하고 세부 기능은 소개문/게시물에서 설명 |
| 플랫폼 종속 | Threads 정책·노출·기능 변화에 이름이 묶임 | 플랫폼명을 브랜드명에 넣지 않고 채널은 유통면으로 취급 |
| 지원 기대치 상승 | Threads 답글이 고객센터로 변함 | 공개 답변 범위, 버그 신고 경로, 개인정보를 받지 않는 원칙을 고정 |
| 사용자 데이터 노출 | 사례·스크린샷·답글에 개인정보가 포함됨 | 동의 없는 이름·이메일·위치·화면 캡처를 게시하지 않고 사례는 비식별화 |
| 경쟁·상표 충돌 | 유사 이름을 빠르게 채택함 | 후보 확정 전 검색·도메인/핸들·상표 검토를 별도 기록; 검색 결과만으로 법적 안전을 단정하지 않음 |
| 단기 반응 편향 | 초기 좋아요·팔로워를 이름의 적합성으로 오독 | 답글의 구체성, 앱 관련 질문, 재사용 가능 문장을 우선 관찰 |
| 공개 실행 경계 붕괴 | 후보 평가가 계정 생성·게시로 이어짐 | 모든 산출물은 proposal-only, 사용자 명시 승인 전 외부 행동 금지 |

## 금칙

### 이름·프로필 금칙

- 확보하지 않은 핸들을 확보한 것처럼 표시하지 않는다.
- 상표·법적 안전성·플랫폼 정책 적합성을 검색 몇 번으로 보증하지 않는다.
- 경쟁사·유명 브랜드를 연상시키는 철자 변형으로 유입을 노리지 않는다.
- `official`, `help`, `support`, `verified` 등 신뢰·권한을 암시하는 표기를 근거 없이 붙이지 않는다.
- 앱이 제공하지 않는 기능, 정확도, 보안, 수익, 성장, 자동화 결과를 이름이나 소개문에서 약속하지 않는다.
- 이름에 특정 국가·언어·사용자군을 넣을 때 실제 운영 범위와 근거 없이 포괄성을 주장하지 않는다.

### Threads 운영 금칙

- 사용자 동의 없이 후기·DM·스크린샷·계정명·개인정보를 재게시하지 않는다.
- 답글을 유도하기 위해 가짜 사용자, 가짜 대화, 허위 사용 경험을 만들지 않는다.
- 같은 문장과 링크를 반복 게시하거나 관련 없는 인기 대화에 도배하지 않는다.
- 제품 결함·장애·정책·가격을 확인하지 않고 단정하거나 변명으로 덮지 않는다.
- 민감한 건강·재정·법률·안전 판단을 앱이 대신한다고 말하지 않는다.
- 논쟁·비판에 자동 반박, 조롱, 개인정보 공개, 보복성 인용으로 대응하지 않는다.
- Threads 계정 생성, 핸들 선점, 프로필 변경, 게시·예약, DM·댓글, 광고·외부 링크 공유를 이 문서 작성만으로 실행하지 않는다.

## 운영 전 체크리스트

- [ ] 앱의 핵심 문제, 첫 사용자, 금지된 약속이 한 문서에 고정되어 있는가
- [ ] 후보 10개 이상에 같은 점수표를 적용했는가
- [ ] 추천 1개와 백업 2개의 장점·탈락 조건이 기록되어 있는가
- [ ] 핸들 가용성, 유사 계정, 상표 검토가 `확인됨/미확인/추가 확인 필요`로 구분되어 있는가
- [ ] 소개문과 첫 Threads 3개가 이름이 암시하는 역할과 일치하는가
- [ ] 개인정보·저작권·지원 문의·위기 대응 경계가 정해져 있는가
- [ ] 사용자 명시 승인 없이는 공개 행동을 하지 않는가

## Marketer 인계

- **Planner:** 앱의 핵심 문제와 첫 사용자를 확정해 `앱 연결성` 판단의 기준 문장을 제공한다.
- **Developer:** 후보 생성, 철자 변형, 유사 계정·핸들 확인 가능 여부를 사실과 미확인으로 분리해 기록한다.
- **Operator:** 추천 후보 1개와 백업 2개를 승인 대기 상태로 관리하며, 계정 생성·변경·게시를 실행하지 않는다.
- **Genie/Red:** 후보 점수의 근거가 이름 감상에 머물지 않는지, 과장 약속·오인·공개 실행이 섞이지 않았는지 검증한다.

## 현재 결론

앱 정보가 추가되기 전에는 특정 후보명을 최종 확정하지 않는다. 현재 Marketer의 판단은 **행동형 또는 문제형 후보를 우선 평가하고, Threads에서 반복 가능한 발화와 브랜드 역할의 명료성을 하드 게이트로 삼는다**는 것이다. 후속 후보 목록이 들어오면 이 표로 1위·백업 2개를 좁히되, 핸들 선점과 공개 게시 없이 내부 결정안으로만 남긴다.
