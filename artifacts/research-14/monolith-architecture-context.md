## 한 줄 답

모놀리스는 특정 유행을 보완하려고 "발명된" 아키텍처라기보다, 초기 소프트웨어와 엔터프라이즈 애플리케이션에서 **분산 실행·분산 데이터·분산 배포가 만들 복잡도를 피하고 한 프로세스/한 배포 단위 안에서 기능을 빨리 통합하기 위해 자연스럽게 달성된 기본형**에 가깝다. "모놀리스"라는 이름은 대체로 SOA, microservices처럼 더 쪼개진 구조가 논의되면서 사후적으로 대비되는 말이 되었다.

## 핵심 포인트 5개

1. **보완한 것은 분산 복잡도다.** 네트워크 호출, 서비스 간 계약, 독립 배포, 데이터 일관성, 관측성, 운영 자동화가 약한 상태에서 기능을 여러 실행 단위로 나누면 시스템보다 조율 비용이 먼저 커진다. 모놀리스는 이 조율 비용을 한 코드베이스와 한 배포 단위 안으로 접어 넣는다.
2. **얻은 것은 단순한 개발·테스트·배포 경로다.** 한 애플리케이션으로 빌드하고 배포하므로 초기에 로컬 실행, 트랜잭션, 디버깅, 릴리스 관리가 쉽다. Martin Fowler의 `MonolithFirst`도 새 시스템의 도메인 경계가 아직 불명확할 때 먼저 하나로 만들고 경계가 보이면 나누는 전략을 설명한다.
3. **초기에는 '아키텍처 선택'보다 '기본값'이었다.** 전통적인 엔터프라이즈 앱은 UI, 데이터베이스, 서버 애플리케이션으로 나뉘어도 서버 애플리케이션 내부 기능은 하나의 실행·배포 단위에 들어가는 일이 많았다. 그래서 당시에는 굳이 "모놀리스"라고 부르지 않고 그냥 애플리케이션이었다.
4. **한계는 규모가 커질수록 드러난다.** 코드가 커지고 팀이 늘면 작은 변경도 전체 빌드·테스트·배포를 요구하고, 특정 기능만 독립적으로 확장하기 어렵다. 모듈 경계가 느슨하면 내부 결합이 빠르게 누적된다.
5. **마이크로서비스는 모놀리스의 반대가 아니라 한계가 실제로 커졌을 때의 비용 전환이다.** 독립 배포, 팀 자율성, 부분 확장, 기술 선택 자유를 얻지만, 그 대가로 분산 시스템 운영, API 계약, 장애 전파, 관측성, 데이터 분산 문제를 떠안는다.

## 보완한 것 / 얻은 것 / 나중에 생긴 한계

| 관점 | 내용 |
|---|---|
| 보완한 것 | 초기 시스템에서 분산 구조가 만들 네트워크·운영·데이터 일관성·조직 조율 복잡도 |
| 얻은 것 | 한 코드베이스, 한 런타임, 한 배포 단위, 쉬운 로컬 개발, 단순한 트랜잭션과 디버깅, 빠른 제품 초기 속도 |
| 나중에 생긴 한계 | 전체 재배포, 독립 확장 어려움, 팀 간 충돌, 코드 경계 붕괴, 기술 스택 고착, 장애 영향 범위 확대 |

## 역사적 프레이밍

"모놀리스"는 대개 처음부터 목표 이름으로 세운 설계라기보다, 이후 microservices/SOA 같은 분산·서비스 지향 구조를 설명하려고 기존 방식에 붙인 대비어로 읽는 편이 자연스럽다. Fowler와 Lewis는 microservices를 설명하면서 먼저 "single unit"으로 지어진 전통적 애플리케이션을 비교 대상으로 둔다. 이 문맥에서 모놀리스는 "나쁜 옛날 방식"이 아니라, 도메인 경계·팀 경계·운영 성숙도가 충분히 생기기 전까지 복잡도를 줄이는 응집형 기본값이다.

## 판단 기준

모놀리스가 보완하는 문제와 모놀리스가 만드는 문제는 시점이 다르다.

- **초기/작은 팀/도메인 불명확:** 모놀리스는 좋은 기본값일 가능성이 높다. 무엇을 나눠야 하는지 아직 모르기 때문이다.
- **팀·도메인·트래픽·배포 빈도 증가:** 모놀리스 내부의 결합이 병목이 되기 시작한다. 이때 모듈러 모놀리스, 서비스 분리, microservices 같은 선택지가 비용을 바꾼다.
- **운영 자동화 부족:** microservices가 장점보다 부담을 먼저 만든다. 독립 서비스는 자동화된 배포, 모니터링, 장애 대응, API 관리가 있어야 이득이 난다.

## 출처와 근거

- Martin Fowler, "Microservices" (2014): monolithic style을 "single unit" 애플리케이션과 비교해 설명하고, microservices는 작고 독립 배포 가능한 서비스들의 조합으로 정의한다. https://martinfowler.com/articles/microservices.html
- Martin Fowler, "MonolithFirst" (2015): 새 시스템에서 도메인 경계가 불명확할 때 monolith-first 전략이 유효할 수 있음을 설명한다. https://martinfowler.com/bliki/MonolithFirst.html
- Martin Fowler, "Microservice Trade-Offs" (2015): microservices가 독립 배포와 확장성을 주지만 분산 시스템의 비용을 만든다는 trade-off를 정리한다. https://martinfowler.com/articles/microservice-trade-offs.html
- IBM Think, "What is monolithic architecture?": monolithic architecture를 여러 비즈니스 기능이 하나의 코드베이스에서 실행되는 전통적 개발 모델로 설명한다. https://www.ibm.com/think/topics/monolithic-architecture
- NIST SP 800-204: microservices가 작은 코드베이스, 빠른 개발·테스트·배포, 독립 팀, 독립 확장을 촉진한다고 설명한다. 이는 반대로 전통적 모놀리스에서 커질 수 있는 병목을 보여준다. https://csrc.nist.gov/pubs/sp/800/204/final
