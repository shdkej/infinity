# build-14 Marketer Output

## 역할 판단

이 페이지는 성과를 자랑하는 대시보드가 아니라, 매일 한 번 열어 보고 "오늘 시스템이 어디까지 살아 있는지" 확인하는 상태판이어야 한다. 첫 버전의 말은 크고 멋진 비전보다 짧은 확인감이 중요하다.

가치 프레임:

- 매일의 시스템 상태를 한눈에 본다.
- 좋아진 것보다 끊긴 것, 쌓인 것, 다시 봐야 할 것을 먼저 알아차린다.
- 기술 로그를 사용자 생활 언어로 바꿔서, 다음 행동 하나를 고르기 쉽게 한다.

## 페이지 이름 후보

1. 오늘의 시스템
2. 시스템 컨디션
3. 하루 상태판
4. 운영 리듬
5. 오늘의 신호

추천: **오늘의 시스템**

이유: 매일 여는 페이지의 습관성이 가장 강하고, 기술 대시보드처럼 차갑지 않다. "시스템"이라는 단어는 사용자의 4레이어 운영 맥락과 맞고, "오늘의"가 첫 화면을 일일 확인 루틴으로 고정한다.

서브 이름:

- 내부 경로명: `Daily System Metrics`
- 사용자 표시명: `오늘의 시스템`
- 문서/운영 맥락: `Daily System Metrics Visualization`
- 브라우저 title 후보: `오늘의 시스템 - Daily Metrics`

이름 원칙:

- 매일 열어도 부담 없는 이름을 쓴다.
- "대시보드", "관제", "컨트롤 타워"는 필요할 때만 보조 설명으로 둔다.
- 페이지 이름은 성과보다 상태를 말한다.
- 영어명은 개발/운영 문맥에만 두고, 화면 첫 인상은 한국어로 잡는다.

## 첫 화면 카피

Headline:

> 오늘 시스템이 어디까지 굴러갔는지 봅니다.

Supporting copy:

> 기록, 자동화, 회고, 알림의 흐름을 하루 단위로 모았습니다. 좋아진 숫자보다 끊긴 루프와 다시 볼 신호를 먼저 확인합니다.

더 짧은 버전:

> 오늘 시스템이 어디까지 굴러갔는지 봅니다.
> 끊긴 루프와 다시 볼 신호를 하루 단위로 확인합니다.

MVP 첫 화면 추천 세트:

- 제목: `오늘의 시스템`
- 상태 문장: `오늘은 확인이 필요한 신호가 2개 있습니다.`
- 보조 문장: `자동화, 일감, 기록, 지식 흐름을 하루 단위로 모았습니다.`
- 주요 행동: `먼저 볼 신호 확인`
- 최신성 문구: `마지막 갱신: 2026-08-05 22:38 UTC`

상태별 문구:

- 정상: `큰 끊김 없이 돌아가고 있습니다.`
- 주의: `작은 끊김이 있습니다. 오늘 한 번만 확인하면 됩니다.`
- 확인 필요: `흐름이 멈춘 지점이 있습니다. 먼저 이 항목부터 보세요.`
- 데이터 없음: `아직 오늘 지표가 없습니다. 마지막 정상 데이터로 보여드립니다.`
- 오래된 데이터: `오늘 데이터가 아직 갱신되지 않았습니다. 마지막 갱신 기준으로 봅니다.`

첫 화면 톤:

- 페이지가 사용자를 평가하지 않는다.
- "잘했다/못했다"보다 "돌아간다/끊겼다/다시 본다"를 쓴다.
- 숫자보다 오늘 판단할 한 줄을 먼저 둔다.
- 상태 문구는 평온해야 한다. 장애가 있어도 겁주는 말보다 복구 첫 행동을 붙인다.

## 지표 라벨 점검

기술 내부어는 사용자가 매일 이해할 말로 바꾼다. 라벨은 "어떤 시스템 컴포넌트가 성공했나"보다 "내 하루 운영에 어떤 신호인가"를 보여야 한다.

권장 라벨:

- `cron_success_rate` -> 자동화 완료율
- `cron_failures` -> 실패한 자동화
- `heartbeat_count` -> 확인한 루틴
- `message_sent_count` -> 보낸 알림
- `memory_write_count` -> 남긴 기록
- `memory_search_count` -> 다시 꺼낸 기억
- `infinity_active_count` -> 진행 중인 일감
- `infinity_archived_count` -> 정리된 일감
- `review_completed` -> 회고 완료
- `daily_tracking_entries` -> 하루 기록
- `agent_errors` -> 에이전트 오류
- `stale_tasks` -> 멈춘 작업
- `deploy_checks` -> 화면 확인

Developer 계약 기준 4개 그룹의 MVP 라벨:

- `automation` -> 자동화
- `cron_ok` -> 완료된 자동화
- `cron_failed` -> 실패한 자동화
- `no_reply` -> 답하지 않은 루틴
- `infinity` -> 일감 흐름
- `active` -> 진행 중
- `archived` -> 정리됨
- `waiting` -> 대기 중
- `new_intents` -> 새로 들어온 일감
- `life` -> 하루 운영
- `plan_blocks` -> 계획한 블록
- `check_done` -> 마무리 확인
- `energy` -> 에너지 기록
- `knowledge` -> 지식 흐름
- `daily_review` -> 회고 기록
- `wiki_updates` -> 정리된 지식
- `query_gaps` -> 남은 질문

라벨 원칙:

- `job`, `task`, `intent`, `artifact`, `heartbeat` 같은 내부어는 첫 화면에서 풀어 쓴다.
- 수치가 높을수록 좋은지 나쁜지 애매한 지표는 보조 문구를 붙인다. 예: "실패한 자동화", "멈춘 작업".
- 사용자가 매일 행동으로 옮길 수 없는 지표는 첫 버전에서 뒤로 보낸다.
- 성공 숫자만 크게 보이지 않게 한다. 끊김, 누락, 재확인 신호가 같은 위계로 보여야 한다.

숫자 보조 문구 원칙:

- 전일 대비 증감은 "늘었습니다/줄었습니다"보다 맥락을 붙인다. 예: `실패가 1건 늘었습니다.`
- 좋고 나쁨이 애매한 숫자는 판단을 보류한다. 예: `새 일감 3개`는 좋은 신호도 부담 신호도 될 수 있다.
- 행동 가능한 숫자만 첫 화면에 둔다. 바로 확인할 수 없는 세부 수치는 그래프 아래로 내린다.
- 원자료를 모르는 사용자도 이해할 수 있게 단위를 붙인다. 예: `3건`, `2개 블록`, `최근 7일`.

## 매일 행동으로 이어지는 카피 원칙

이 페이지의 카피는 "동기부여"가 아니라 "다음 확인"을 만든다.

좋은 흐름:

1. 오늘 상태를 말한다.
2. 흔들린 묶음을 하나 짚는다.
3. 사용자가 할 첫 행동을 한 줄로 남긴다.

예시:

- `자동화 실패가 1건 있습니다. 먼저 실패한 루틴을 확인하세요.`
- `진행 중인 일감은 유지됐고, 새 일감이 1개 들어왔습니다. 오늘은 대기 중인 항목만 보면 됩니다.`
- `오늘 회고 기록이 아직 없습니다. 마무리 시간에 한 줄만 남기면 됩니다.`
- `지식 흐름은 정상입니다. 남은 질문은 없습니다.`

피해야 할 흐름:

- 숫자를 보여주고 해석을 사용자에게 전부 맡긴다.
- 모든 지표를 같은 긴급도로 말한다.
- 좋은 숫자만 강조해 실제 끊김을 숨긴다.
- 자동화가 사용자 대신 판단한다는 뉘앙스를 준다.

CTA 원칙:

- CTA는 명령보다 손잡이처럼 쓴다.
- 첫 버전의 CTA는 하나만 둔다.
- CTA는 화면 안에서 실제로 이어질 수 있는 행동이어야 한다.

CTA 후보:

- `먼저 볼 신호 확인`
- `멈춘 항목 보기`
- `오늘 흐름 확인`
- `데이터 갱신 상태 보기`

피할 CTA:

- `생산성 분석 시작`
- `AI 인사이트 확인`
- `전체 최적화 실행`
- `완벽한 루틴 만들기`

## 8시간 MVP 카피 기준

MVP에서 반드시 지킬 기준:

- 첫 화면 5초 안에 `오늘 상태`, `흔들린 묶음`, `다음 행동`이 보여야 한다.
- 최소 3개 지표군은 한국어 라벨과 한 줄 해석을 가진다.
- sample/fallback 데이터는 실제 데이터처럼 말하지 않는다.
- 데이터가 없거나 오래됐을 때도 페이지가 침묵하지 않는다.
- 공개 가능성이 있는 화면이므로 원문 로그, 사람 이름, 장소, 메시지 내용은 카피에 넣지 않는다.
- 화면 문구는 하루 운영을 돕는 톤으로 제한한다.

MVP에서 제외할 카피:

- 장기 생산성 평가
- AI가 사용자를 분석/판정한다는 표현
- 인생 전체 데이터를 통합한다는 표현
- 자동 해결, 자동 최적화 약속
- 성과 과시형 문구
- 사적인 생활 원자료를 암시하는 문구

MVP에서 허용할 정보 전달:

- 날짜별 집계
- 상태 라벨
- 전일 대비 변화
- 마지막 갱신 시각
- 오늘 볼 항목 1개
- 공개-safe aggregate라는 안내

MVP에서 보류할 정보 전달:

- 상세 로그 drilldown
- 개인 메시지/캘린더/위치 기반 설명
- 비용/토큰 상세 수치
- 에이전트 내부 프롬프트나 실행 payload
- intent 제목 전체 공개

## 민감 정보 경계

공유하거나 공개하지 않아야 할 정보:

- 개인 Telegram 메시지 원문, 채팅 상대, 그룹명, 메시지 ID
- 이메일, 캘린더, 여행 일정, 위치 이동, 건강·수면·소비 같은 개인 원자료
- API key, 토큰, SecretRef, 환경변수 값, 서버 경로 중 자격증명 위치
- 내부 에이전트 프롬프트 전문, 시스템 설정 전문, 실패 로그의 원문 payload
- 공개 전인 Infinity intent의 세부 내용, 사적 프로젝트명, 외부 권한/배포 URL 중 비공개 대상

첫 버전에서는 공개 페이지보다 개인용 운영 화면으로 본다. 외부에 보여야 한다면 날짜별 집계값과 익명화된 상태만 남기고, 원문 이벤트와 사람·장소·계정 정보는 제거한다.

## 첫 버전에서 버릴 표현

버릴 표현:

- "당신의 생산성을 극대화하는 AI 운영 허브"
- "모든 삶의 데이터를 한눈에 통합"
- "완벽한 자기관리 시스템"
- "시스템의 모든 문제를 자동으로 해결"
- "압도적인 성장 그래프"
- "AI가 당신의 하루를 판정합니다"
- "마스터 컨트롤 타워"
- "내 삶의 모든 데이터를 통합 분석"
- "압도적인 효율을 만드는 시스템 관제센터"
- "오늘의 점수"
- "AI가 찾아낸 문제"
- "자동으로 개선됩니다"

이유: 과하고, 차갑고, 실제 첫 버전의 약속보다 크다. 이 페이지는 사용자를 평가하거나 설득하는 곳이 아니라, 매일의 흐름을 확인하고 다음 행동을 고르는 곳이어야 한다.

## 다음 역할에 넘길 규칙

- Developer는 첫 화면의 주요 숫자를 "성공/실패/멈춤/기록"처럼 행동 가능한 묶음으로 보여준다.
- Planner는 지표군을 많이 늘리기보다, 매일 확인할 이유가 있는 3-5개 묶음으로 시작한다.
- Operator는 공개/배포 경로가 생길 경우 원자료 비노출, 집계값, 날짜 범위 제한을 기본값으로 둔다.

## 계승한 기준

- `build-14` intent의 첫 버전 목표: 8시간 안에 매일 볼 수 있는 첫 시각화 페이지.
- Planner의 정보 구조: 오늘 상태 -> 핵심 지표 -> 날짜별 그래프 -> 오늘의 확인 목록.
- Developer의 데이터 계약: `life`, `infinity`, `automation`, `knowledge` 4개 그룹과 public-safe aggregate JSON.
- Operator의 보안 경계: 공개 페이지에는 원문 로그와 개인 원자료를 넣지 않는다.
- Sam Samuel 디자인 기준: Calm Technology, Warm Minimalism, 사용자를 평가하지 않는 조용한 상태판.

## 이번에 새로 배운 것

- 이 페이지의 핵심 약속은 "더 열심히 살게 하는 것"이 아니라 "오늘 시스템이 끊겼는지 조용히 보게 하는 것"이다.
- 지표 카피는 성과보다 복구 가능성을 먼저 말해야 한다.
- `오늘의 시스템`은 내부 운영 도구지만, 사용자가 매일 다시 열 수 있어야 하므로 페이지 이름부터 낮은 압력이어야 한다.
- MVP에서는 인사이트보다 최신성, 상태, 다음 행동 한 줄이 더 중요하다.
