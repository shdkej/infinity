# GitHub 에이전트 스킬 지형과 마스터님용 후보 — 탐색형 재조사

> 범위: 공개 GitHub 저장소와 공식 문서를 다시 열어, 설치 여부를 결정하는 심사 대신 **무엇이 있고 실제로 어디에 쓸 수 있는지**를 설명합니다. 설치·클론·스크립트 실행·계정 연결은 하지 않았습니다.

## 한 문장 결론

마스터님에게 지금 가장 쓸모 있는 것은 “더 엄격한 리서치 스킬”이 아니라 **웹 자료를 수집하는 경로를 상황별로 고르는 스킬**, **여행 영상과 인터뷰를 관찰 가능한 메모로 바꾸는 스킬**, 그리고 **앱 아이디어를 빠르게 좁히는 스킬**입니다. 이미 있는 `deep-research`는 도입 결정이 필요할 때만 남기고, 평소에는 이 세 가지를 탐색형 브리프의 보조 도구로 쓰는 구성이 맞습니다.

## GitHub에서 보이는 세 층

### 1) 런타임·형식 층: 스킬은 “기능 추가”보다 작업 설명서에 가깝습니다

OpenClaw과 GitHub Copilot 모두 스킬을 `SKILL.md`가 든 폴더(지침, 선택적 스크립트·자료)로 설명합니다. 즉 스킬 하나가 웹 검색 능력이나 계정 권한을 새로 만들어 주는 것은 아닙니다. 이미 있는 브라우저·파일·API 도구를 **언제 어떤 순서로 쓰고, 무엇을 결과로 남길지** 정하는 재사용 가능한 플레이북입니다. 따라서 마스터님 환경에서는 “어떤 스킬이 많나”보다 “우리의 도구·안전 경계와 충돌하지 않고 반복할 일이 있나”가 더 중요한 선택 기준입니다.

공식 OpenAI `openai/skills`는 현재 deprecated이며, 최신 예시는 `openai/plugins`와 Codex 플러그인 가이드를 보라고 안내합니다. 반대로 OpenClaw 문서는 제3자 스킬을 신뢰할 수 없는 코드로 보고, 활성화 전에 내용을 읽고 위험한 도구에는 샌드박스를 쓰라고 명시합니다. 즉 GitHub 스킬 탐색은 플러그인 장터 쇼핑이 아니라, 좋은 업무 절차를 찾아 **현재 운영 방식에 맞게 가져오는 일**로 보는 편이 정확합니다.

### 2) 대형 컬렉션 층: 넓지만, 그대로 일괄 설치할 대상은 아닙니다

`agent-skills-collection`은 3,104개를 수집했지만 그중 기본 설치 가능은 2,574개, 형식 문제로 격리된 것은 530개, 고위험 정적 신호가 있는 것은 115개라고 공개합니다. 이 숫자는 생태계가 넓다는 신호이지, 수천 개를 설치할 이유는 아닙니다. 이 컬렉션의 가치에는 카탈로그·원저작자 연결·형식 검사·중복 표기가 있고, 단점은 미러링된 스킬이 기본적으로 미검토라는 점입니다.

`awesome-agent-skills`와 `github/awesome-copilot`은 다른 역할을 합니다. 전자는 코드 리뷰, 테스트, 디버깅, 문서화, 감사처럼 **개발 작업의 작은 반복 절차**를 골라 쓰기 좋은 목록이고, 후자는 에이전트·instructions·skills·plugins를 함께 모아 검색/발견용으로 좋습니다. 둘 다 “묶음 전부 설치”보다 필요할 때 원문 `SKILL.md` 하나를 읽고 가져오는 용도가 더 적합합니다.

### 3) 좁은 실전 워크플로 층: 마스터님에게는 이쪽이 가장 가치 있습니다

`valtterimelkko/agent-workflow-skills`는 대형 목록보다 적은 수의 실전 워크플로에 집중합니다. 특히 `web-data-acquisition`, `thematic-analysis`, `video-deep-understanding`, `handoff`, `artifact-variations`처럼 여행·콘텐츠·제품 관찰을 바로 다루는 항목이 있어 현재 관심사와 맞습니다. 다만 일부 스크립트는 자체 API 키, 프록시, 로컬 환경을 전제한다고 명시하므로, 지침의 핵심만 적응시키고 스크립트는 검토 전 실행하지 않는 전제가 필요합니다.

## 마스터님에게 쓸 만한 후보 5개

### A. `web-data-acquisition` — 가장 먼저 쓸 후보

**쓰임:** 시장 지형, 경쟁 서비스, 사용자 후기, 여행지 정보처럼 “웹에서 무엇을 어떤 경로로 얻을 것인가”가 먼저인 조사입니다. 검색 결과를 많이 모으는 대신, 공식 문서·페이지 추출·다중 페이지 수집·로그인 필요 여부·API 가능 여부를 먼저 분기합니다.

**마스터님 활용 장면:**
- 세계여행 중 현지 서비스·예약·규정·가격을 조사할 때, 검색 스니펫을 사실처럼 쓰지 않고 공식 운영자 페이지와 현지 1차 정보로 갈 경로를 고릅니다.
- “모두의 창업 지원”에서 경쟁 제품의 가격·온보딩·후기 지형을 볼 때, 공개 랜딩페이지, 앱스토어, 커뮤니티, 제품 문서를 목적별로 나눕니다.
- OpenClaw/AI 도구 사례를 조사할 때, 벤더 홍보 자료와 실제 사용 사례·문서를 한 덩어리로 섞지 않게 합니다.

**현재 환경과의 관계:** 이미 브라우징 도구와 탐색형 리서치 규칙이 있으므로 별도 설치보다는 `탐색형 조사 = 수집 경로 선택 → 핵심 원문 몇 개 열람 → 한국어 설명 브리프`라는 짧은 절차로 흡수하는 편이 좋습니다. 이 후보가 가장 실용적인 이유는 조사 품질을 높이면서도 Red·HTML·다역할 게이트를 만들지 않기 때문입니다.

### B. `thematic-analysis` — 여행과 제품 통찰을 자산으로 만드는 후보

**쓰임:** 인터뷰, 여행 메모, 사용자 피드백, 회고처럼 긴 텍스트에서 반복되는 행동·불편·욕구를 코드와 테마로 묶는 방식입니다. 단순 요약과 달리 “어떤 문장이 어떤 테마를 지지하는가”를 남길 수 있습니다.

**마스터님 활용 장면:**
- 여행 중 만난 사람들의 대화나 현장 메모에서 “예약 불안”, “언어 장벽”, “혼자 여행의 루틴”처럼 앱 아이디어의 씨앗을 분류합니다.
- 미니 워크숍 피드백에서 참여자가 실제로 어려워한 지점과 단순 호감 표현을 분리합니다.
- 사용성 테스트·DM·설문이 쌓일 때, 기능 요청 목록이 아니라 문제의 패턴을 뽑습니다.

**주의:** 개인 대화나 민감한 메모는 외부 서비스에 넣지 않고 현재 워크스페이스에서 최소 범위로 처리해야 합니다. 지금은 데이터가 충분히 쌓이는 시점에만 호출하는 보조 스킬이 적절하며, 매일 회고를 억지로 코딩하는 자동화는 아닙니다.

### C. `video-deep-understanding` — 여행 영상을 ‘나중에 쓸 관찰’로 바꾸는 후보

**쓰임:** 영상의 말(자막/트랜스크립트)과 실제 화면·장면을 함께 보며, 단순 대본 요약으로 놓치는 행동·공간·감정 변화를 기록합니다.

**마스터님 활용 장면:**
- 여행 영상에서 “좋은 장면”을 추리는 데 그치지 않고, 장소의 소리·동선·대기·표정처럼 이후 영상 편집과 앱 인사이트에 재사용할 관찰을 남깁니다.
- 워크숍 촬영본에서 참가자의 질문·멈춤·화면 조작을 함께 보며 다음 수업의 마찰 지점을 찾습니다.

**주의:** 현재 YouTube 콘텐츠의 자막·음성·화면 추출은 마스터님의 명시 승인이 있을 때만 진행하는 규칙이 있습니다. 그래서 이 후보는 즉시 자동화가 아니라, 사용자가 영상 분석을 요청했을 때 적용할 **분석 프레임**으로만 보관하는 것이 맞습니다.

### D. `app-discovery-scrutiny` — 나중의 도입/투자 판단용, 지금의 기본 리서치용은 아님

**쓰임:** 앱 틈새를 Build/Pivot/Kill 같은 강한 결론으로 좁히는 사업성 평가입니다. 사용자 문제, 경쟁, 수익 가능성, 실행 난도를 한 번에 비교하려는 경우에 맞습니다.

**마스터님 활용 장면:** 여행에서 얻은 관찰이 여러 개 쌓인 뒤, 어느 한 아이디어를 실제 앱으로 만들지 결정할 때입니다. 예를 들어 “여행자 간 짐 보관 매칭”처럼 구체적 문제 하나에 대해, 해결할 가치와 대체재를 구조적으로 비교할 수 있습니다.

**왜 지금 기본값이 아닌가:** 이 스킬은 마스터님이 원치 않은 ‘판정 모드’를 유도하기 쉽습니다. 지금 합의한 기본값은 사례·시장·도구 지형을 편하게 보는 탐색형이므로, “만들까/도입할까/돈 될까”라고 명시할 때만 꺼내는 것이 좋습니다.

### E. `anti-over-engineering` — 시스템 운영에 가장 작지만 유용한 보조 후보

**쓰임:** 요청보다 큰 구조, 불필요한 게이트, 과한 추상화가 붙는 것을 막습니다. 새 기능을 만들기보다 “이번 요청의 최소 완료 정의가 무엇인가”를 계속 확인하게 하는 성격입니다.

**마스터님 활용 장면:** 바로 이번처럼 탐색형 리서치가 계획·Red·HTML·원격 아카이브 절차로 부풀어 오르는 상황, 혹은 작은 운영 수정이 여러 에이전트·대형 태스크로 번지는 상황에서 유용합니다. 기존 운영 규칙과 겹치는 면은 있지만, 적용 범위를 ‘요청한 결과와 직접 연결되지 않는 절차는 기본적으로 제외’로 좁히면 가치가 있습니다.

## 지금 설치보다 먼저 적용할 운영 방식

1. **탐색형 리서치:** `web-data-acquisition`의 분기만 사용합니다. 결과물은 “무엇이 있는지 → 대표 사례 3~5개 → 왜 흥미로운지 → 불확실성 → 다음에 더 볼 한 곳” 형태의 긴 한국어 브리프입니다. 권고·점수·Red·HTML은 기본으로 넣지 않습니다.
2. **관찰이 쌓일 때:** 여행/워크숍/피드백 텍스트에는 `thematic-analysis`를 적용합니다. 결과물은 테마 3~5개와 각 테마를 뒷받침하는 원문 맥락, 아직 판단하지 말아야 할 공백입니다.
3. **영상 분석을 명시 요청할 때:** `video-deep-understanding`의 관찰표를 사용하되, YouTube 추출은 별도 승인 규칙을 지킵니다.
4. **결정이 명시될 때만:** `app-discovery-scrutiny` 또는 기존 `deep-research`로 전환합니다. 이때만 추천·도입 여부·비용/리스크 비교와 강화된 검증이 의미를 갖습니다.

## 설치하지 않는 것이 좋은 것

- **리서치 오케스트레이터를 또 하나 설치하는 것:** 기존 `deep-research`와 유사한 조사 스킬을 겹쳐 설치하면, 이번에 문제였던 단계·상태·검증 체계의 중복이 다시 생길 가능성이 큽니다.
- **수백~수천 개 컬렉션의 일괄 설치:** 형식·원저작자·의존성·실행 권한이 서로 다른 스킬이 한꺼번에 들어오면, 어떤 지침이 우선하는지 알기 어려워집니다.
- **API 키·프록시·로그인 전제를 가진 스크립트:** 스킬 설명만으로 안전성을 판단하지 말고, 실제 `SKILL.md`, 참조 스크립트, 네트워크 목적지, 저장 경로를 먼저 읽어야 합니다.

## 추천 우선순위

1. **지금 적용:** `web-data-acquisition`의 ‘수집 경로 선택’ 방식 — 설치 없이 탐색형 리서치 기본 흐름에 반영.
2. **자료가 쌓이면 적용:** `thematic-analysis` — 여행/사용자 통찰을 앱·워크숍 소재로 바꾸기.
3. **명시 요청 시 적용:** `video-deep-understanding` — 여행 영상/워크숍 영상 분석.
4. **결정 시에만 적용:** `app-discovery-scrutiny` + 기존 `deep-research`.
5. **운영 보조:** `anti-over-engineering`의 최소 범위 질문을 Infinity 디스패처 규칙에 흡수.

이 브리프는 후보 지형과 활용 시나리오를 설명하는 탐색형 조사입니다. 각 후보의 실행 스크립트, 라이선스, 네트워크 호출을 전수 감사하거나 설치 적합성을 보증하지 않습니다. 다음 행동은 설치가 아니라, 앞으로의 일반 조사에서 `web-data-acquisition`식 소스 경로 선택을 적용해 실제 브리프가 더 읽기 쉬워지는지 한 번 확인하는 것입니다.
