## 1. 왜 자주 고장나는가: 대표 실패 패턴

자동화 시스템은 크게 6개 구조적 취약 지점에서 반복적으로 고장난다.

### 1.1 트리거 실패 (Trigger)
- **크론 드리프트**: timezone 오류, DST 전환, 스케줄러 재시작 누락
- **이벤트 유실**: webhook 전달 실패, 메시지 큐 overflow, 이벤트 순서 역전
- **비결정성 트리거**: 조건이 모호하거나 외부 상태에 의존
- *진단 어려움*: 작업이 실행조차 되지 않았다는 사실 자체를 알기 어렵다

### 1.2 실행 실패 (Execution)
- **타임아웃**: 예상보다 오래 걸리는 작업, 무한 대기
- **자원 고갈**: 메모리 누수, 디스크 포화, 커넥션 풀 소진
- **환경 의존성 파손**: 패키지 업데이트, API 버전 변경, 설정 파일 삭제

### 1.3 상태 실패 (State)
- **비멱등 작업**: 중복 실행 시 데이터 오염 (중복 레코드, 중복 알림)
- **스테일 상태**: 캐시 미갱신, 오래된 설정 파일 참조
- **동시 실행 충돌**: 이전 실행이 아직 끝나지 않았는데 다음 실행 시작

### 1.4 의존성 실패 (Dependency)
- **외부 API 파괴적 변경**: 응답 스키마 변경, 엔드포인트 폐기
- **인증 만료**: API 키, OAuth 토큰, SSL 인증서 만료
- **네트워크 파티션**: DNS 실패, 일시적 접근 불가

### 1.5 관측성 부재 (Observability)
- **무음 실패**: 에러가 났지만 로그·알림 없이 조용히 종료
- **알림 피로**: 너무 많은 알림 → 진짜 장애를 놓침
- **컨텍스트 없는 로그**: "에러 발생"만 있고 어떤 입력·상태였는지 모름

### 1.6 핸드오프 실패 (Handoff)
- **부분 완료 후 중단**: 앞 단계는 실행됐지만 뒤 단계가 끊긴 상태
- **보상 트랜잭션 없음**: 실패 시 이미 실행된 작업을 되돌릴 방법 없음

## 2. 무엇이 단단하게 만드는가: 설계 원칙

### 원칙 1: 멱등성 (Idempotency) — 가장 중요한 단일 속성
같은 작업을 여러 번 실행해도 결과가 동일해야 한다.
- 생성 전 존재 여부 확인 (`upsert` / `if not exists`)
- 외부 알림 중복 방지: 발송 전 발송 이력 확인
- 처리 토큰(idempotency key) 부여

### 원칙 2: 재시도 + 백오프 (Retry with Backoff)
실패 즉시 재시도하지 않는다.
- 지수 백오프 + 지터: `wait = min(base * 2^attempt + random_jitter, max_wait)`
- 최대 재시도 횟수 고정 (무한 재시도 금지)
- 재시도 가능 에러 vs 불가 에러 명시적 구분 (일시 장애 vs 영구 오류)

### 원칙 3: 체크포인트 (Checkpoint)
긴 작업은 중간 상태를 저장한다.
- 각 단계 완료 후 상태 기록
- 재시작 시 마지막 체크포인트부터 재개
- 체크포인트는 외부(DB, 파일, 큐)에 저장 — 프로세스 메모리만 믿지 않음

### 원칙 4: 실패 격리 (Failure Containment)
한 부분의 실패가 전체를 멈추지 않게 한다.
- 각 작업 단위를 독립적으로 처리
- 실패한 항목만 격리 (dead letter queue)
- 회로 차단기 (Circuit Breaker): 반복 실패 시 일시 중단, 나중에 재시도

### 원칙 5: 수동 우회 (Manual Override)
자동화가 막혔을 때 사람이 개입할 수 있어야 한다.
- 수동 트리거 버튼 또는 CLI
- 부분 재실행 (특정 단계만 다시)
- 강제 skip (이미 완료된 것으로 마킹)

### 원칙 6: "덜 똑똑하게" 설계
복잡한 자동화는 더 많은 실패 지점을 만든다.
- 조건 분기 최소화
- 결정을 에이전트에 위임하지 않고 규칙으로 고정
- 예측 불가능한 입력은 수동 처리로 넘기기

## 3. 관측성 (Observability) 구조

### 3.1 구조화 로깅
최소 포함 필드:
- `ts`: 타임스탬프
- `job`: 작업 이름
- `run_id`: 실행 단위 ID (한 번의 실행을 추적)
- `step`: 현재 단계
- `status`: success / error / skipped
- `input`: 입력 요약
- `error`: 에러 메시지 (있을 때)
- `retry`: 재시도 횟수

### 3.2 알림 설계 원칙
"신호만 울려야 한다":
- 연속 N회 실패 시 알림 (단발 실패는 재시도로 처리)
- 마지막 성공 시각이 임계값 초과 시 알림 (트리거 실패 감지)
- 알림에는 즉시 대응 명령어 또는 runbook 링크 포함
- 알림 억제(muting) 기간 설정 (유지보수 시간)

### 3.3 실행 이력
- 언제 실행됐고, 성공/실패였는지
- 얼마나 걸렸는지
- 재시도가 있었다면 몇 번째에 성공했는지

## 4. 복구성 (Recoverability) 설계

### 4.1 빠른 재실행
- 실패한 작업만 재실행 가능해야 함 (전체 처음부터 X)
- 재실행 명령어가 문서화되어 있어야 함

### 4.2 Runbook (최소 구조)
1. **증상**: 어떤 에러/알림이 발생했는가
2. **진단**: 로그 어디를 보는가, 어떤 명령어로 상태를 확인하는가
3. **조치**: 재시도/롤백/skip 명령어

### 4.3 롤백 경로
- 가역 작업: DB 변경은 트랜잭션 / git 커밋은 revert
- 불가역 작업(외부 발송, 결제): 보상 트랜잭션 또는 수동 조치 절차 명시

## 5. 어디에 먼저 투자해야 하는가

### 개인 자동화 우선순위

1. **관측성 (Observable)**: 실패를 알 수 없으면 아무것도 고칠 수 없다
   - 최소: 실패 시 알림 1개 (Telegram, 이메일, 슬랙)
   - 이상적: 구조화 로그 + 알림

2. **멱등성 (Idempotent)**: 재실행해도 안전하게
   - 중복 생성/발송 방지

3. **수동 우회**: 자동화가 막혀도 수동으로 할 수 있어야 함
   - 수동 실행 명령어 문서화

4. 이후 여유가 있으면: 재시도 로직 → 체크포인트

### 팀/서비스 자동화 우선순위

1. **관측성**: 구조화 로그 + 메트릭 + 알림 (runbook 링크 포함)
2. **멱등성 + 재시도**: 안전한 재실행 보장
3. **체크포인트**: 긴 작업의 중간 상태 저장
4. **Runbook**: 누구나 대응 가능하게
5. **Circuit Breaker**: 외부 의존성 장애 격리

## 6. 점진적 하드닝 프레임워크

"처음부터 완벽"보다 "단계별로 단단하게"가 현실적이다.

### Level 1 — 볼 수 있게 (Observable)
*목표: 실패를 알 수 있다*
- [ ] 실패 시 알림 1개
- [ ] 실행 로그 (언제 실행됐고 성공/실패했는지)
- [ ] 수동 재실행 방법 문서화

### Level 2 — 재실행 안전하게 (Retryable)
*목표: 실패해도 안전하게 다시 시도할 수 있다*
- [ ] 멱등성 보장 (중복 실행 방지 또는 안전)
- [ ] 재시도 + 지수 백오프
- [ ] 동시 실행 방지 (lock / mutex)

### Level 3 — 격리하고 복구 (Resilient)
*목표: 한 실패가 전체를 망가뜨리지 않는다*
- [ ] 실패 격리 (dead letter queue)
- [ ] Circuit Breaker (외부 의존성 장애 격리)
- [ ] Runbook (장애 대응 절차)
- [ ] 자동 롤백 또는 보상 트랜잭션

---

## 7. 공통 적용 원칙 요약

개인과 팀/서비스 모두에 적용 가능한 핵심 5원칙:

| 원칙 | 적용 형태 | 우선순위 |
|------|-----------|----------|
| **실패를 보이게** | 로그 + 알림 | 가장 높음 |
| **재실행을 안전하게** | 멱등성 | 높음 |
| **실패를 국소화** | 격리, Circuit Breaker | 중간 |
| **수동 복구 경로** | Runbook, 수동 우회 | 중간 |
| **덜 똑똑하게** | 조건 분기 최소화 | 중간 |
